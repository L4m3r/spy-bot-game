# «Шпион»: Telegram-бот и прототип Mini App

TypeScript + grammY + Cloudflare Workers + SQLite-backed Durable Objects. Один GameRoom на комнату и один UserLimits на пользователя. D1, отдельный сервер и домен не нужны.

## Mini App: интерактивный прототип

```sh
npm run preview:miniapp
```

Откройте [локальный предпросмотр](http://127.0.0.1:8793). Для прототипа достаточно Node.js: зависимости бота устанавливать не нужно. Слева находятся демонстрационные сценарии и переключатели темы, ширины, увеличенного текста и системных отступов. Эти элементы не входят в интерфейс Mini App. Кнопка «Добавить игрока» имитирует приход друзей: создание комнаты → ещё два участника → раздача → личная карточка → следующий раунд с подтверждением.

В `prototype/miniapp` представлены главная, комната организатора и участника, приглашение, закрытая комната, личные карточки игрока и шпиона, вход после раздачи, правила и поиск по всем 24 локациям. Роль раскрывается только по нажатию и скрывается при уходе со страницы или потере активности. Системные отступы и цвета учитываются без платформенной развилки. SDK Telegram подключён для темы и доступных нативных кнопок; вне Telegram используются HTML-кнопки.

В сценарии «Сбой сообщения бота» роль уже назначена и доступна в Mini App; ошибка относится только к сообщению в чате. Она не заменяет кнопку открытия карточки и не требует ручного повтора от организатора. Это целевое поведение прототипа: существующий бэкенд повторяет отправку сообщений, но ещё не предоставляет API личной карточки для Mini App. При интеграции нужен авторизованный доступ к собственной роли независимо от статуса доставки; блокировку следующей раздачи на время незавершённых отправок также нужно согласовать с этим сценарием.

Это прототип на вымышленных данных: он не вызывает игровые RPC, не отправляет сообщения в Telegram, не сохраняет комнаты и не публикуется с Worker. Скопированное приглашение ведёт на локальный сценарий предпросмотра. Следующий этап — проверка `initData` на сервере и подключение экранов к существующим GameRoom/UserLimits. Сервер должен возвращать только личную карточку текущего участника, не `spyId` или локацию для всех игроков. Таймер, голосование и счёт в концепцию не добавлены: обсуждение остаётся голосовым.


## Что уже работает

- Один пользователь одновременно состоит только в одной комнате, как организатор или участник.
- `/game` в личке отправляет новое сообщение с текущей комнатой, даже если старое сообщение удалено или не доставлено. Если комнаты нет — создаёт новую.
- `/leave` выводит участника из комнаты. Организатору предлагает подтвердить закрытие комнаты для всех.
- Максимум 10 созданий за скользящий час; вступления, восстановление комнаты и новые раунды квоту не расходуют.
- Приглашение по ссылке, список игроков, выход, закрытие комнаты.
- От 3 до 12 игроков. Один случайный шпион; остальные получают общую локацию.
- Личные карточки, общий список возможных локаций `/locations`.
- Следующий раунд для того же состава с подтверждением. Соседние раунды имеют разные локации.
- Подключившиеся после раздачи участвуют со следующего раунда.
- Повторная отправка неотправленных карточек сохраняет прежние роли и локацию.
- Через 24 часа после последнего успешного действия в комнате удаляются её данные. Фоновые отправки срок не продлевают.

Обсуждения, обвинения и угадывание происходят голосом. Бот не ведёт таймер раунда, голосование или счёт.

## Что нужно для запуска

1. Создать бота у [@BotFather](https://t.me/BotFather) командой `/newbot` и получить токен.
2. Иметь аккаунт [Cloudflare](https://dash.cloudflare.com/) с доступом к Workers. Для этого прототипа предусмотрен Workers Free с SQLite-backed DO; действуют лимиты тарифа.
3. Node.js 22+ и npm на компьютере, с которого выполняется запуск.

Токен хранится локально в `.dev.vars`, затем загружается в Cloudflare как Secret. Не публикуйте этот файл и не отправляйте токен в чат. `.gitignore` исключает файл из Git.

## Первый запуск

Откройте терминал в папке проекта.

```sh
npm ci
npm run init:secrets
```

Откройте `.dev.vars` в редакторе и замените значение `BOT_TOKEN` токеном из BotFather. `WEBHOOK_SECRET` уже сгенерирован случайным образом. Если файл уже существует, команда его не перезаписывает.

Авторизуйтесь в Cloudflare:

```sh
npx wrangler login
```

Wrangler откроет браузер: войдите в свой аккаунт и разрешите доступ. Пароль Cloudflare передавать боту или в чат не нужно. Если доступно несколько аккаунтов, укажите нужный `account_id` в `wrangler.jsonc`.

Проверьте проект:

```sh
npm run check
npm test
npm run build
```

Опубликуйте Worker:

```sh
npm run deploy
```

Перед публикацией проверяется формат секретов. Команда отправляет код и оба секрета из `.dev.vars` в Cloudflare. SQLite-backed DO создаётся миграцией автоматически. При первом запуске Wrangler может предложить настроить поддомен `workers.dev`. Название Worker можно изменить в `wrangler.jsonc` до публикации.

Скопируйте выданный адрес, например `https://spy-telegram-bot.example.workers.dev`, и запустите:

```sh
npm run setup:telegram
```

Скрипт попросит HTTPS-адрес Worker, проверит его доступность и совпадение webhook-секрета, проверит токен через `getMe`, настроит команды и webhook. Секреты читаются из `.dev.vars`; в аргументы командной строки и вывод они не попадают.

Теперь откройте своего бота, отправьте `/game` и поделитесь приглашением. В группе бота добавлять не требуется.

## Проверка в настоящем Telegram

1. Создайте комнату с первого аккаунта.
2. С двух других аккаунтов откройте приглашение и нажмите «Старт».
3. Убедитесь, что в комнате три участника, нажмите «Раздать карточки».
4. Проверьте: одному пришёл шпион, двум — одинаковая локация.
5. Запустите следующий раунд и убедитесь, что сначала появляется подтверждение.
6. Закройте комнату и откройте прежнее приглашение: оно должно сообщить, что комната закрыта.

Автотесты подменяют только Telegram API; обработчики, SQLite DO, Alarms и восстановление объекта работают в локальном runtime Cloudflare. Настоящий Telegram и облачный аккаунт без ваших учётных данных не проверяются.

## Как устроен проект

```text
Telegram → POST /webhook → Worker с grammY
                            └─ команды комнаты и приглашения → UserLimits по Telegram user ID
                                                                  └─ RPC → GameRoom по коду комнаты

GameRoom: SQLite + Alarm для отправки сообщений и удаления комнаты
UserLimits: SQLite + Alarm для проверки ссылки и очистки данных пользователя
```

| Файл | Назначение |
| --- | --- |
| `src/index.ts` | Проверка webhook-секрета, команды и кнопки, маршрутизация |
| `src/room.ts` | Состав комнаты, раздача, постоянная очередь отправки, Alarms |
| `src/user-limits.ts` | Одна активная комната, лимит созданий, восстановление и очистка ссылки |
| `src/rpc.ts` | Копирование данных RPC и освобождение результата и объекта вызова, в том числе при исключении |
| `src/model.ts` | Модель данных, локации и срок хранения |
| `src/view.ts` | Сообщение комнаты и клавиатура |
| `wrangler.jsonc` | Worker, binding и миграция SQLite DO |
| `scripts/setup-telegram.mjs` | Настройка Telegram после публикации |
| `test/bot.test.mjs` | Интеграционные сценарии в Miniflare |

У комнаты есть один Alarm. Он назначается на ближайшее событие: отправку, повторную попытку или истечение срока. После обработки назначается следующее время. `setInterval` и постоянно работающий процесс не используются.

Во время выполнения `alarm()` промежуточные сохранения и входящие команды не назначают ещё один короткий Alarm: текущий обработчик дочитывает очередь и назначает следующий вызов один раз в конце пакета. При исключении восстановление обеспечивает повтор текущего Alarm со стороны Cloudflare. Уже назначенное более раннее пробуждение сохраняется; если за это время TTL продлили, обработчик при пробуждении перепроверит срок и назначит оставшееся время.

Состав и раздача сохраняются до отправки карточек. Изменения состояния сериализуются в коротких секциях `blockConcurrencyWhile`; сетевые вызовы выполняются вне них. Повторные update_id обрабатываются без повторной мутации в пределах сохранённых последних 256 событий. Номер раунда в кнопке дополнительно защищает от устаревших и повторных раздач.

Ошибки сети, 429 и ошибки сервера Telegram повторяются автоматически с задержкой, максимум пять попыток на задачу. Для 429 учитывается `retry_after`. После неуспеха организатор видит, кому карточка не отправилась, и может повторить отправку. При блокировке бота игроку сначала нужно разблокировать его.

Список участников обновляется редактированием сообщения комнаты. Если игрок удалил это сообщение, бот создаёт новое. `/game` и кнопка «Показать комнату» всегда отправляют новое сообщение; последующие изменения состава и раунда обновляют уже его. Повторная доставка одного update_id не создаёт вторую задачу отправки. Команды работают без доступа к старым сообщениям. После изменения списка команд повторите `npm run setup:telegram`, чтобы `/leave` появился в меню Telegram; сама команда работает сразу после деплоя.

### Лимиты и синхронизация

`UserLimits` адресуется по Telegram user ID; общего объекта для всех пользователей нет. Все действия с комнатами, включая приглашения, проходят через него. Операции одного пользователя выполняются последовательно. `/game` восстанавливает собственную или чужую текущую комнату и не создаёт новую, пока участие действительно. Попытка вступить в другую комнату предлагает `/game` и `/leave`. Новые комнаты ограничены десятью созданиями за последние 60 минут. Закрытие комнаты квоту не возвращает.

Перед созданием или вступлением сохраняется резервирование: код комнаты, исходная команда, идентификатор участия и абсолютный срок действия запроса. Намерение и alarm восстановления записываются одной локальной транзакцией. После RPC `GameRoom` подтверждает наличие именно этого участия. При потерянном ответе проверка обнаруживает уже записанного игрока; при сбое до записи повторяется исходная операция. Квота создания списывается один раз. Пока исход неизвестен, слот пользователя остаётся занят. Если срок исходного запроса истёк, сначала проверяется фактическое участие: оно может оставаться действительным, поскольку другие игроки продлили TTL. Только подтверждённое отсутствие позволяет освободить слот. Запоздалый запрос с истёкшим сроком не принимается комнатой.

Выход и закрытие также сначала сохраняют намерение. Слот освобождается только после подтверждения комнаты. Повторный выход после потерянного ответа безопасен. `GameRoom` сохраняет идентификаторы завершённых участий до истечения TTL: старое вступление не возвращает вышедшего игрока даже после очистки последних 256 update_id, старый выход не удаляет новое участие того же пользователя. Повторные Telegram update_id отсекаются также на стороне пользователя. Удаляются ещё не отправленные задачи вышедшего игрока; повторная раздача не отправляет карточку прежнего участия после повторного входа.

Источником истины о существовании, составе и TTL служит `GameRoom`; `UserLimits` управляет единственным слотом пользователя. Общей транзакции между DO нет. Связь односторонняя: комната никогда не вызывает пользовательский объект. После закрытия или TTL ссылки участников очищаются лениво при следующем действии либо пользовательском alarm. Исключение RPC не считается признаком удаления комнаты. Проверки срока не продлевают комнату.

Незавершённые действия восстанавливает alarm, даже без новых сообщений Telegram. При сбое он сохраняет намерение и назначает следующую попытку с увеличением задержки до 60 секунд; восстановление не ограничено встроенными шестью повторами alarm. При обычной работе alarm проверяет комнату в последний известный срок TTL. Без участия и свежей квоты данные пользователя удаляются через 24 часа после последнего обращения.

### Переход с предыдущей версии

Классы DO и bindings остаются прежними; новая миграция Wrangler не нужна. Старые комнаты не содержат индекса участия гостей и могли включать одного пользователя одновременно в несколько игр. Такие комнаты **закрываются при первом обращении или alarm после обновления**. Их приглашения больше не действуют; `/game` создаёт новую комнату. Старая квота создания пользователя сохраняется. Это намеренный переход схемы для прототипа: переносить старые списки участников как достоверный индекс единственного участия нельзя.


## Хранение и ограничения прототипа

- TTL — ровно 24 часа от последнего успешного действия с комнатой. Просмотр без нажатий и разговор голосом не считаются активностью. На каждом обращении срок проверяется независимо от Alarm.
- При истечении TTL удаляются данные комнаты и её alarm. При явном закрытии содержимое удаляется сразу, а до истечения срока первоначального запроса создания хранится только отметка закрытия с alarm очистки (не более 24 часов). Она блокирует запоздавший RPC создания. Старое приглашение не создаёт комнату заново. Конструктор не создаёт данные и не продлевает TTL.
- Отправленные сообщения с карточками остаются в Telegram после удаления комнаты.
- Если Telegram принял сообщение, а объект перезапустился до сохранения подтверждения, возможна повторная отправка той же карточки. Гарантировать доставку «ровно один раз» через Telegram API нельзя.
- Закрытие комнаты или выход игрока не могут отменить запрос отправки, который уже ушёл в Telegram.
- Рейтинга и истории завершённых игр нет. UserLimits хранит только текущую ссылку, временные отметки квоты и данные для безопасного повтора команды.
- Размещение DO оставлено автоматическим. Его код и SQLite colocated; входной Worker может находиться в другом дата-центре. Location hint можно добавить позже после измерений.
- Публичный `/health` проверяет доступность Worker; он не подтверждает валидность токена или доставку карточек.
- Тестовая дата совместимости совпадает с конфигурацией Worker. Зависимости зафиксированы в `package-lock.json`; используйте `npm ci` для воспроизводимой установки.

## Разработка и повторная публикация

```sh
npm run dev
```

Локальная разработка использует отдельное локальное состояние. Telegram не сможет доставить webhook на `localhost` без публичного HTTPS-туннеля; для проверки логики достаточно `npm test`. Для экспериментов с настоящим Telegram используйте отдельного тестового бота.

После изменений выполните проверки и `npm run deploy`. Если адрес и webhook-секрет не менялись, заново настраивать webhook не нужно. После изменения `WEBHOOK_SECRET` повторите `npm run setup:telegram`.

## Проверки PR и Workers Builds

Workflow `.github/workflows/ci.yml` запускается только для pull request в `main`: установка по lock-файлу, TypeScript, интеграционные тесты и сборка Worker. Новый коммит в тот же PR отменяет устаревшие проверки. Деплоем занимается Cloudflare Workers Builds после push в `main`.

GitHub Actions и Workers Builds используют Node.js 24 из `.node-version`. Actions закреплены полными SHA; GitHub Token имеет только `contents: read`, а credentials checkout не сохраняются. Cloudflare Secrets в GitHub Actions не используются.

В существующем Worker `spy-telegram-bot` откройте Settings → Build, подключите репозиторий и задайте:

| Настройка Workers Builds | Значение |
| --- | --- |
| Репозиторий | `L4m3r/spy-bot-game` |
| Production branch | `main` |
| Root directory | `/` (корень репозитория) |
| Build command | `npm run check && npm test && npm run build` |
| Deploy command | `npm run deploy:ci` |

Cloudflare запросит разрешение GitHub-интеграции на доступ к репозиторию. Авторизацию деплоя настройте в Workers Builds; Cloudflare может автоматически создать API token. Секреты `CLOUDFLARE_API_TOKEN` и `CLOUDFLARE_ACCOUNT_ID` в GitHub не требуются. Если они были добавлены для прежней схемы, их можно удалить из GitHub.

Workers Builds выполняет собственные проверки перед публикацией: отдельный успешный запуск GitHub Actions не является условием для его деплоя. Если любая команда в Build command завершится с ошибкой, публикация остановится.

`BOT_TOKEN` и `WEBHOOK_SECRET` остаются в Cloudflare в Settings → Variables & Secrets и сохраняются при обычном деплое кода. В build variables и GitHub их добавлять не нужно. Для Workers Builds используется `npm run deploy:ci`, которому не требуется локальный `.dev.vars`. Локальная команда `npm run deploy` по-прежнему загружает секреты из `.dev.vars`.

Настройка подключения в панели Cloudflare выполняется отдельно от коммита workflow. После подключения проверьте первый build/deploy. Подробности: [настройки Workers Builds](https://developers.cloudflare.com/workers/ci-cd/builds/configuration/).

Документация: [grammY на Workers](https://grammy.dev/hosting/cloudflare-workers-nodejs), [DO и SQLite](https://developers.cloudflare.com/durable-objects/best-practices/access-durable-objects-storage/), [Alarms](https://developers.cloudflare.com/durable-objects/api/alarms/), [секреты Cloudflare](https://developers.cloudflare.com/workers/configuration/secrets/).
